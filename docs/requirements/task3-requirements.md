# 赛题 3 需求基线：图像采集压缩与智能预处理加速

## 依据与判定规则

- **最高依据**：`local_refs/problem/安路.pdf`，PDF 页 17--25 的“选题三”。本文件的“明确要求”只来自该范围。
- **硬件可行性依据**：`docs/hardware/platform-baseline.md` 所列 `02_hardware` 资料。它说明板上有什么，不扩张赛题要求。
- **官方示例/课程资料**若使用，只能证明曾采用过的路线，不能把设备节点、像素格式、分辨率或帧率变成赛题要求。本次基线未以 `03_course` 为需求依据。

## 1. 赛题原文明确定义的强制要求

来源：赛题 3“一、赛题简介/1.硬件分工架构/2.硬性交付基础任务”，PDF 页 17--18。

| 编号 | 强制交付 | 归属 | 原文依据 |
|---|---|---|---|
| R1 | 以 PH1A90SEG324 FPGA 与 RK3576 异构平台完成机器视觉前端到后端智能分析链路。 | 共同 | 页 17--18 |
| R2 | 完成 MIPI CSI 图像传感器的 FPGA 驱动 IP，至少单路高清图像实时采集。 | FPGA | 页 18，任务 1） |
| R3 | FPGA 以硬件并行方式实现至少 3 种基础预处理；题中列出灰度化、高斯滤波、直方图均衡，并说明三选一作基础、其余两项也必须硬件并行实现。因此实现计划应覆盖这三项，不能用纯软件替代。 | FPGA | 页 18，任务 2） |
| R4 | FPGA 实现 JPEG 或 LZ77 **任一种**硬件图像压缩加速模块，并输出压缩后的低带宽数据流。 | FPGA | 页 18，任务 3） |
| R5 | 在 FPGA 与 RK3576 间完成 MIPI 或 PCIe **二选一**高速通道，稳定传输压缩图像帧。 | 共同 | 页 18，任务 4） |

“完整链路”与职责描述还明确 FPGA 负责传感器原始数据采集、预处理、JPEG/LZ77 等压缩、像素缓存/时序；RK3576 负责 AI 推理以及交互、存储、网络、参数配置和控制（页 18）。后半组功能是架构职责与系统设计方向；其中 NPU 推理是 R6 的硬性交付，交互/存储/网络本身没有在“硬性交付基础任务”中被逐项规定为独立必交功能。

## 2. 输入、处理、传输、AI、显示与控制

### 明确要求

| 环节 | 需求结论 | 依据 |
|---|---|---|
| 输入 | 输入来自 **MIPI CSI 图像传感器**，由 FPGA 驱动 IP 采集，至少一路高清、实时。没有规定具体传感器型号、分辨率、位宽、颜色编码或帧率。 | 页 18，任务 1） |
| 处理 | FPGA 硬件并行预处理（R3），再由硬件 JPEG 或 LZ77 压缩（R4）。 | 页 18，任务 2）--3） |
| 传输 | 向 RK3576 传的是压缩图像帧；芯片间高速通道只能在 MIPI 与 PCIe 中选一条完成必做交付。 | 页 18，任务 3）--4） |
| AI | RK3576 的 NPU 做本地轻量化**目标检测**并输出识别结果；“识别、分类”等出现在架构说明，R6 的硬性交付措辞是目标检测。 | 页 18 |
| 显示 | 赛题 3 的硬性交付没有规定必须 HDMI/MIPI-DSI/屏幕显示，也没有规定显示原图、压缩图、识别框或 UI。识别结果的呈现媒介需项目自行定义。 | 页 18；页 24--25 |
| 控制 | 参数配置与系统控制被列为 RK3576 后端职责，但控制 UI、协议、按键和远程控制没有强制细节。 | 页 18 |

### 合理工程推导（不是新增赛题条款）

- 应为图像帧定义时间戳/帧号、尺寸、像素格式或压缩格式、有效载荷长度、校验/错误统计和背压规则，否则无法证明稳定传输、计算端到端延迟或正确解压/推理。
- 若选 JPEG，压缩流必须能被 RK 侧确定性解析、转成模型输入；赛题未要求 JPEG 的具体采样格式、质量因子、EXIF/JFIF 封装或 RGB24。若选 LZ77，应另约定原始像素格式、帧边界和解码路径。
- “至少单路高清实时”要求选择一个可由实际传感器、FPGA 缓存、互连带宽、RK 解码/预处理与 NPU共同持续达成的工作点，并用 R7 指标实测，而不能用课程示例的固定工作点替代验证。
- NPU 检测结果至少应能与输入帧关联（帧号/时间戳）并具有可演示输出；显示、串口或网络均可能是工程方案，待确认评审偏好。

### 官方示例采用但并非赛题强制的方式

本赛题 PDF 的平台介绍仅列板卡资源（页 9--11），没有给出赛题 3 的指定软件示例参数。本项目中如存在课程示例的 `/dev/video73`、`/dev/video22`、RGB24、1080p 或特定帧率，它们只能是实现起点；**均不是 R1--R7 的要求**，也不得假设 video 节点号固定。

## 3. 性能、验收与演示

### 明确的验收项

- 必须可演示 R2--R6 全链路，并提交 R7 的五类量化数据（页 18）。
- “量化评分指标”再次列出单路 MIPI CSI、三种硬件预处理、JPEG/LZ77 编码、FPGA--RK 传输、NPU 推理和完整性能数据（页 24）。
- 赛题没有给出一套适用于所有项目的最低帧率、最大延迟、最低压缩率、准确率、固定分辨率或固定 JPEG 参数。评审应以实测工作点和报告方法验收。

### 不应误作统一硬指标的数字

页 20--23 的“工业/安防/车载/农林/医疗”分级场景，出现 1080P、60 fps、4K@30 fps、压缩率/准确率/延迟等数字；它们是不同应用场景的简单/中级/高级展示示例，不是“硬性交付基础任务”的通用阈值。页 24“基础必做项”中把“单路稳定采集；实现双路同步”并列，而页 25 又将双路列作创新拓展的中级项，文本层级不一致，见待确认项 Q2。

### 建议验收演示（工程推导）

现场连续运行：MIPI 传感器 → FPGA 三项预处理 → JPEG/LZ77 → 选定 MIPI/PCIe → RK 解码/适配 → NPU 检测 → 可观察结果输出；同时展示资源占用和 R7 五项测量的采样条件、统计口径及结果。此流程是证明强制任务的最小演示，不等同于强制 HDMI 显示。

## 4. 分工任务

### Linux / RK3576 侧

- 部署、调用并量测 NPU 轻量化目标检测；输出可关联到输入帧的检测结果（R6、R7）。
- 实现所选 MIPI/PCIe 接收端、压缩帧拆包/解码或送模型前转换，以及缓冲与错误统计（R5 的共同部分）。
- 提供参数配置、结果呈现、数据保存/网络或调试导出等后端能力，具体方式待接口协议确定（页 18，架构职责）。

### FPGA 侧

- MIPI CSI 传感器接收与控制 IP、至少单路实时采集（R2）。
- 灰度化、高斯滤波、直方图均衡的硬件流水/并行实现，以及帧/行缓存和时序控制（R3）。
- JPEG 或 LZ77 硬件压缩、输出帧封装（R4）。
- 实现选定的 FPGA 端 MIPI 或 PCIe 链路，并导出资源占用和链路/处理计数（R5、R7）。

### 双方共同接口

- 决定 MIPI 或 PCIe；写明角色、代际/速率、lane、复位/上电时序、错误恢复与板上资源冲突。
- 冻结帧封装：压缩算法、输入像素格式描述、宽高、帧号/时间戳、载荷长度、校验、分片、流控、端序与版本。
- 统一量测边界：采集时刻、压缩完成、RK 收到完整帧、推理开始/结束；共同产出 R7 报告。
