# Skill Installation Contract

This page defines the self-contained installation entry points for `readable-verilog-generator` v2.0.0. The entry scripts sit beside `SKILL.md`; runtime reads only package projections and configuration and never depends on a development-machine `agents-md-generator` installation.

## Entry points and shared backend

The package directory provides three entry points:

- `install.ps1`: PowerShell parameters are `-Platform`, `-Source`, `-PlatformRoot`, `-TargetDir`, `-Replace`, `-Yes`, `-DryRun`, and `-Json`.
- `install.sh`: accepts the equivalent GNU long options.
- `install.bat`: forwards to the same-level PowerShell entry point.

The three wrappers only read the same-level bootstrap projection, discover the Python runtime declared by the manifest, forward arguments, and preserve the backend exit code. Installation behavior belongs to the manifest-selected Python backend.

## Authoritative configuration

Installation behavior is controlled by JSON files under `config/installer/`:

- `platform-catalog.json`: platform IDs, aliases, root resolution, skill directory, detection rules, and metadata projections.
- `installer-manifest.json`: package identity, version source, projection paths, runtime candidates, status text, exit codes, transaction templates, and source policy.
- `verification-cases.json`: isolated verification cases, command flags, precondition files, and expected status/exit code.
- `*.schema.json`: minimum structure and required-field contracts.

Release tooling also reads `config/runtime-manifest.json` and its release-only `installer_manifest` role. That role binds `config/installer/release-installer-manifest.json`, which describes bundle-relative resources without changing the skill-root-relative paths used by the runtime installer. `platform-overrides.json` and `installer-projection.schema.json` are release-bound resource declarations.

The JSON projections under `assets/installer/` and the same-level bootstrap descriptor are generated by an explicit command. Identical authoritative inputs must produce byte-identical projections. Installation fails immediately when the manifest, catalog, projection, or digest disagree.

## Source payload requirements

`--Source` must point to a versioned release directory whose root contains the `RELEASE_RECEIPT.json` filename declared by the manifest. The receipt must declare skill identity, version, and per-file SHA-256 entries; an optional per-file size is also checked when declared. The ordinary source-file set must match the receipt exactly. A source checkout, missing receipt, path escape, symlink, forbidden name, or digest mismatch is rejected.

When `--Source` is omitted, only the wrapper package root itself may be used as the source when it satisfies the same release-receipt contract. The installer never treats the current source checkout as a release payload automatically.

## Harness selection and paths

An explicit `--Platform` takes precedence. Without it, the backend selects a unique candidate from the catalog detection rules. Non-interactive calls fail on zero or multiple candidates instead of guessing a default platform. IDs and aliases not declared by the catalog fail closed.

`--PlatformRoot` and `--TargetDir` only override paths explicitly supplied by the caller and still undergo containment, symlink, and source/target overlap checks. One transaction handles exactly one platform and one final target directory.

## Transaction and receipt

The write order is: parse and validate, acquire the target lock, create same-level staging, copy the verified payload, preserve unlisted user files, move the old target to backup, atomically install the new target, verify the installed tree, and atomically write the install receipt. Wrapper-based real writes automatically pass `--replace` and `--yes`, so an existing target is backed up before replacement; direct backend calls still need both flags. The explicit `--Replace` and `--Yes` wrapper parameters remain accepted for compatibility.

On failure, the backend attempts to restore the old target. A failed recovery returns the manifest-declared `RECOVERY_REQUIRED` status and preserves quarantine evidence. The install receipt records package identity, platform ID, projection/release digests, installed-tree digest, preserved files, and transaction status; it does not record a complete user home directory, credentials, or environment values.

`--DryRun` performs only parse, projection, receipt, and path checks. It does not create a lock, staging directory, backup, quarantine directory, or install receipt. Automatic replacement and backup apply only to real wrapper writes.

## Machine protocol and verification

`--Json` emits one JSON object; status text and exit codes come from the manifest. Human-readable output uses `> INFO: [Python]`, `> WARNING: [Python]`, and `> ERR: [Python]` prefixes.

Development checks:

```text
python -B -m scripts.python.installation.projection --skill-root <skill-root> --manifest <manifest-json> --catalog <catalog-json> --output <platform-projection> --manifest-output <manifest-projection> --env-output <bootstrap-env>
python -B -m scripts.python.validation.installer_audit audit --skill-root <skill-root> --manifest <manifest-json> --catalog <catalog-json> --cases <cases-json> --report <audit-report>
python -B -m scripts.python.validation.installer_audit smoke --skill-root <skill-root> --manifest-env <bootstrap-env> --cases <cases-json> --report <smoke-report>
```

These commands write only inside caller-selected report and temporary boundaries. Isolated smoke is product-level configuration evidence; it does not replace canonical pytest, remote regression, real Harness installation, synthesis, implementation, timing, or hardware acceptance.

## Non-goals

This version does not download online content, auto-upgrade, batch-install across Harnesses, modify global Harness configuration, install software versions, control Harness processes, or automatically publish, commit, or push. New platforms, path templates, status values, cases, or runtime candidates require updates to the authoritative JSON, schemas, projections, and registry first.
